# Ledger Core Detail ORM Mapping v1

## 1. Scope

QM2-P0-002A2a2a maps exactly four existing domain details: `ChangedFile`,
`ChangedSymbol`, `TestExecution`, and `ImplementationArtifact`. It adds static
SQLAlchemy metadata only. Reference/annotation records, mappers, Repository,
Session/Unit of Work, migration, schema creation, database access, Indexer,
API, and UI are outside this contract.

## 2. Domain vs ORM Boundary

The frozen A1b1 dataclasses and validators remain semantic authority. A1b2
remains authority for identity, replay, append-only, query, version, conflict,
and atomic-batch behavior. These ORM classes define PostgreSQL persistence
shape and selected database-repeated invariants; they do not replace either
contract and expose no business methods.

## 3. Shared Schema and Base

All records subclass `backend.services.api.models.base.Base`, register in its
shared metadata, and explicitly target schema `quantmind2`. No new Base,
Engine, Connection, Session, or runtime metadata action is introduced.

## 4. Technical IDs and Natural Keys

`ChangedFileRecord.changed_file_id` and
`ChangedSymbolRecord.changed_symbol_id` are caller-supplied `VARCHAR(255)`
technical primary keys. A future Mapper/Indexer must derive stable values; the
database supplies no sequence, UUID, default, or generator. Their A1b2 natural
keys remain, respectively, `(implementation_run_id, path, change_type)` and
`(implementation_run_id, file_path, qualified_name)`.

`test_execution_id` and `artifact_id` already exist in the domain and are used
directly as primary keys. The corresponding run-scoped A1b2 natural keys are
also represented as named unique constraints. Because these IDs are primary
keys, the future Indexer must provide globally stable IDs. Exact replay is
decided by Repository identity plus immutable-content equality, never by an
auto-increment value.

## 5. ChangedFile Mapping

`quantmind2.implementation_changed_files` contains `changed_file_id`,
`implementation_run_id`, `path`, `change_type`, nullable `before_hash`,
nullable `after_hash`, and nullable `previous_path`. Hashes are `CHAR(64)`;
paths are `TEXT`; identifiers and enum storage are bounded `VARCHAR`.

The checks distinguish added, deleted, modified, renamed, and unchanged
shapes. Rename requires a nonblank previous path different from the current
path. Unchanged requires equal before/after hashes. A non-rename cannot carry
`previous_path`. Path traversal and repository-relative path semantics remain
domain rules.

## 6. ChangedSymbol Mapping

`quantmind2.implementation_changed_symbols` contains `changed_symbol_id`, run
ID, `file_path`, `qualified_name`, `symbol_type`, and `change_type`.
`qualified_name` is `VARCHAR(512)` and cannot be blank. The A1b2 natural key
excludes `change_type`; therefore a second change type for the same run, file,
and qualified name conflicts rather than creating a second logical record.
The database neither parses Python AST nor treats a qualified name as a path.

## 7. TestExecution Mapping

`quantmind2.implementation_test_executions` contains the domain ID, run ID,
command, purpose, status, three nonnegative counts, nullable not-run reason,
nullable artifact URI, and nullable artifact hash. `passed` requires zero
failures, `failed` requires at least one failure, and `not_run` requires a
nonblank reason while every other status forbids one. Command secret scanning
and URI validation stay in the domain layer.

## 8. ImplementationArtifact Mapping

`quantmind2.implementation_artifacts` contains the domain artifact ID, run ID,
artifact type, path or URI, nullable content hash, nullable schema version, and
nullable nonnegative size. The location is intentionally opaque to the
database; file existence, path safety, URI safety, and content verification
are not persistence-shape concerns.

## 9. Enum Persistence

Enum columns use `VARCHAR` plus explicitly named `CHECK` constraints. Allowed
values are generated by `enum_check_sql` from A1b1 `FileChangeType`,
`SymbolType`, `SymbolChangeType`, and `TestExecutionStatus`. Tests compare the
persisted tuples and SQL checks directly to the domain enums. PostgreSQL native
Enum types and duplicated handwritten value lists are not used.

## 10. Primary Keys

The four named primary keys are `pk_qm2_files`, `pk_qm2_symbols`,
`pk_qm2_tests`, and `pk_qm2_artifacts`. No primary key has a Python default,
server default, sequence, or autoincrement identity.

## 11. Foreign Keys

Every record references
`quantmind2.implementation_runs.implementation_run_id` through an explicitly
named foreign key with `ON DELETE RESTRICT`. Details cannot outlive or silently
delete their parent Run.

## 12. Unique Constraints

Named unique constraints preserve A1b2 natural keys:

- file: run + current path + change type;
- symbol: run + file path + qualified name;
- test: run + test execution ID;
- artifact: run + artifact ID.

For a rename, the natural key uses the current `path`; `previous_path` is
retained as immutable provenance and indexed separately.

## 13. Check Constraints

Named checks repeat enum domains, nonblank database values, lowercase SHA-256
shape, nonnegative counts/sizes, TestExecution status combinations, and
ChangedFile change/hash/path combinations. They intentionally do not attempt
filesystem traversal detection, URI credential inspection, command secret
scanning, Git/object existence, replay comparison, or authorization.

## 14. Indexes

File indexes cover run, current path, previous path, change type, and run/path.
Symbol indexes cover run, file, qualified name, symbol type, and run/file.
Test indexes cover run, status, and run/status. Artifact indexes cover run,
type, content hash, and run/type. All names are explicit, globally unique in
the shared metadata, and at most 63 characters.

## 15. Delete Semantics

Foreign keys are restrictive. There is no cascade, `delete-orphan`, soft
delete column, delete method, trigger, or automatic timestamp mutation.

## 16. Append-only Boundary

Append-only is a Repository authorization and transaction rule. The ORM has no
update/delete convenience methods or relationships with cascade semantics, but
static table metadata alone cannot prevent arbitrary privileged SQL updates.

## 17. Rules Enforced by Domain

The domain owns identifier normalization, path traversal/repository-path
safety, command secret-like detection, URI/hash/value validation before
persistence, object construction, immutable state, and direct semantic
invariants.

## 18. Rules Enforced by Repository

The future Repository must own exact-replay equality, immutable conflict
detection, append authorization, parent existence at operation boundaries,
expected version behavior, stable query semantics, relationship graph rules,
and atomic multi-record writes. None is implemented by this task.

## 19. Rules Enforced by Database

The database metadata repeats PK, parent FK, natural uniqueness, enum value
domains, selected nonblank/hash/count/size checks, and the ChangedFile and
TestExecution cross-column combinations. A future migration is required before
any of these constraints exist in PostgreSQL.

## 20. Static DDL Verification

Tests compile all four tables and indexes with the PostgreSQL dialect without
creating an Engine or Session. They verify schema qualification, named
objects, `ON DELETE RESTRICT`, absence of cascade/trigger/secret material, and
metadata-wide name uniqueness. Verification used an existing SQLAlchemy
2.0.51 environment; production requirements pin 2.0.25. Dialect compilation
does not prove migration ordering, schema privileges, server execution, or
real PostgreSQL concurrency/transaction behavior.

## 21. Deferred Reference Tables

`ComponentReference`, `ArchitectureDecisionReference`, `Limitation`, and
`RecommendedTask` mappings are explicitly deferred. No table resembling those
objects is registered by this task.

## 22. Deferred Domain Mappers

No `to_domain`, `from_domain`, mapper, serializer, or deserializer exists.
Stable technical-ID derivation and all domain/ORM conversions remain deferred
until the full mapping surface is known.

## 23. Deferred Migration

No migration, migration version, bootstrap SQL edit, `CREATE SCHEMA`, or
`CREATE TABLE` is added. Metadata remains an unapplied target contract.

## 24. Deferred PostgreSQL Integration

There is no database URL access, credentials access, Engine, Connection,
Session, Unit of Work, production Repository, transaction, or PostgreSQL test.
SQLite is not an acceptable substitute for JSONB/schema/PostgreSQL evidence.

## 25. Handoff to QM2-P0-002A2a2b

The only recommended next task is `QM2-P0-002A2a2b — Ledger Reference and
Annotation ORM Mapping`. It may map the four deferred reference/annotation
objects, but must not reinterpret the four core details or claim that metadata
has been deployed.
